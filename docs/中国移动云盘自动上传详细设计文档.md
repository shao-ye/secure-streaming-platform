# 中国移动云盘自动上传详细设计文档

## 1. 文档目标

本文档用于设计以下能力，当前阶段仅做方案设计与评审，不改业务代码：

- 在后台管理页面“频道管理”页签右上角“设置”中，增加中国移动云盘登录与验证能力
- 在频道配置弹窗中增加录制文件自动上传配置
- 在录制文件完成重命名后自动上传到中国移动云盘
- 给出登录态过期检测、告警、重登录与任务暂停恢复方案

本文档强调两个原则：

- 新增配置必须放入现有“系统设置”和“频道配置”的原有存储结构中，保持结构一致
- 先采用当前项目可落地、风险可控的方案，复杂能力采用分阶段交付

---

## 2. 当前系统现状梳理

## 2.1 系统架构现状

当前项目采用三层架构：

- 前端：Vue 3 + Element Plus
- 业务层：Cloudflare Workers + KV
- 转码层：VPS Node.js + FFmpeg

与本次需求直接相关的职责边界如下：

- 前端负责管理员配置录入、登录验证触发、目标目录选择、状态展示
- Workers 负责保存系统配置、频道配置，并将配置下发给 VPS
- VPS 负责录制文件生成、重命名、恢复修复、上传任务执行

---

## 2.2 当前“系统设置”存储结构

当前后台“设置”弹窗使用接口：

- `GET /api/admin/cleanup/config`
- `PUT /api/admin/cleanup/config`

当前 Workers 实际存储键为：

- `system:cleanup:config`

当前后端可确认已持久化字段为：

```json
{
  "enabled": true,
  "retentionDays": 2,
  "segmentEnabled": false,
  "segmentDuration": 60,
  "updatedAt": "2026-03-16T00:00:00.000Z"
}
```

需要注意的现状问题：

- 前端 `SystemSettingsDialog.vue` 已经录入了 `recoveryScanHours`
- 但当前 Workers `PUT /api/admin/cleanup/config` 尚未将 `recoveryScanHours` 持久化
- 说明“系统设置”当前已经存在前后端字段不完全一致的问题

这对本次设计的启示是：

- 本次新增中国移动云盘配置时，必须同步定义“前端表单结构 / Workers 持久化结构 / VPS 消费结构”
- 避免再次出现前端有字段、后端未存储的情况

---

## 2.3 当前“频道配置”存储结构

当前频道配置接口：

- `GET /api/channel/:channelId/config`
- `PUT /api/channel/:channelId/config`

当前频道数据保存在：

- `channel:{channelId}`

当前 `recordConfig` 结构可确认如下：

```json
{
  "enabled": false,
  "startTime": "08:00",
  "endTime": "17:00",
  "workdaysOnly": false,
  "storagePath": "/var/www/recordings",
  "updatedAt": "2026-03-16T00:00:00.000Z",
  "updatedBy": "admin"
}
```

当前 `preloadConfig` 和 `recordConfig` 都是频道对象下的嵌套对象，因此自动上传配置也应继续放在 `recordConfig` 内部，而不是新建平级根字段。

---

## 2.4 当前录制文件完成点

当前录制文件在以下环节变成最终可上传文件：

- `SimpleStreamManager.renameCompletedSegment()`
- `SimpleStreamManager.renameFinalSegment()`
- `RecordingRecoveryService` 修复历史异常文件后

这意味着自动上传的正确触发时机不是“FFmpeg 开始录制时”，而是：

- 临时文件转为标准 MP4 成功后
- 或服务重启后，异常录制文件被修复并重命名成功后

这是本次上传设计的核心触发点。

## 3. 139 云盘能力调研结论

本节结论基于本次对网页、网络请求和开放平台页面的调研，以及此前已经验证通过的“家庭相册三段式上传”结果。

## 3.1 已验证能力

已确认中国移动云盘“家庭相册”支持服务器侧上传，且已在 VPS 上实测跑通：

- `POST /hcy/group/dynamic/file/create`
- `PUT` 到预签名 EOS `uploadUrl`
- `POST /hcy/group/dynamic/file/complete`

说明以下事实成立：

- 家庭相册上传在技术上可落地
- 上传核心障碍不在文件协议，而在登录态获取、保存、校验与续期

---

## 3.2 普通 Web 登录入口调研结论

在匿名访问 `https://yun.139.com/w/#/` 时，当前网页可见登录入口页签为：

- 短信登录
- 手机登录
- 账号登录

在页面可见层面，本次未看到“扫码登录”作为普通 Web 首页默认入口。

进一步点击“账号登录”后，页面展示了：

- 手机号输入框
- 密码输入框
- 登录按钮

因此，本次设计可以确认：

- **账号密码登录入口存在**
- **短信登录入口存在**
- **二维码登录不应作为当前首选设计方案**

这里强调一下边界：

- 我们确认的是官方 Web 页面存在这些登录入口
- 但尚未确认存在可公开直接调用、稳定、无风控的“第三方账号密码登录 API”

---

## 3.3 开放平台调研结论

`https://open.yun.139.com/` 页面明确展示了开放平台存在，并展示了如下能力描述：

- 上传
- 读取
- 分享
- 自动备份
- 在线播放

页面还展示了：

- 申请能力
- 接入指引
- 技术文档
- 开发者服务协议

这说明中国移动云盘存在面向合作方的正式开放能力体系。

但本次快速调研尚未确认以下能力：

- 是否存在面向个人家庭云/家庭相册的自助式 OAuth 授权接入
- 是否存在可直接嵌入我方后台页面的官方二维码授权组件
- 是否允许无人工审批直接接入个人家庭相册上传

因此当前设计结论是：

- **开放平台存在，说明“正式合作接入”理论可行**
- **但当前项目短期内不应把“开放平台正式合作”当作唯一落地前提**
- **当前项目应优先基于官方 Web 登录态复用 + 已验证上传接口实现**

---

## 3.4 目录/相册选择能力调研结论

### 3.4.1 家庭相册

已观察到家庭相册相关接口，包括但不限于：

- `queryContentList`
- `queryCloudPhoto`
- `queryContentInfo`

这说明家庭相册列表、相册内容列表、相册详情查询是存在网页接口支撑的。

因此家庭相册目标选择器可以设计为：

- 先查询家庭空间
- 再查询该家庭下相册列表
- 供管理员选择具体相册

### 3.4.2 默认文件目录

当前调研中，尚未完成“默认文件目录树接口”的完整抓取与稳定性确认。

因此不能在本阶段承诺“一定能直接做到完整树形目录选择器”。

当前更稳妥的设计建议是分阶段：

- V1：家庭相册支持可视化选择；默认文件目录先支持“手动输入路径 + 验证”
- V1.1：若后续抓到稳定目录列表 API，则升级为懒加载树选择器

这是兼顾落地速度与不确定性的最优方案。

---

## 4. 总体设计结论

本次推荐采用如下路线：

- **登录主方案**：优先支持“账号登录”和“短信登录”两种模式
- **二维码登录**：不作为 V1 主方案，仅保留为预留扩展
- **目标选择主方案**：
  - 家庭相册：做可视化选择
  - 默认文件目录：V1 先做“手动路径 + 验证”，后续升级树选择器
- **上传触发主方案**：在 MP4 标准化重命名完成后触发上传
- **过期处理主方案**：服务端主动探测 + 前端管理员在线提醒 + 任务排队暂停恢复

## 5. 配置模型设计

## 5.1 系统设置结构扩展设计

为了满足“新增配置仍放在原有系统设置结构中”的要求，建议继续沿用：

- KV Key：`system:cleanup:config`
- API：`/api/admin/cleanup/config`

在原结构中扩展一个新的嵌套对象：`cloudDrive`

### 推荐结构

```json
{
  "enabled": true,
  "retentionDays": 2,
  "segmentEnabled": false,
  "segmentDuration": 60,
  "recoveryScanHours": 48,
  "cloudDrive": {
    "enabled": false,
    "provider": "cmcc139",
    "loginMode": "password",
    "account": "13800138000",
    "accountMasked": "138****8000",
    "savePassword": false,
    "passwordEncrypted": "<encrypted>",
    "sessionBundleEncrypted": "<encrypted>",
    "authStatus": "unknown",
    "authMessage": "",
    "lastValidatedAt": "2026-03-16T00:00:00.000Z",
    "estimatedExpireAt": "2026-03-16T12:00:00.000Z",
    "lastValidator": "admin",
    "updatedAt": "2026-03-16T00:00:00.000Z",
    "updatedBy": "admin"
  },
  "updatedAt": "2026-03-16T00:00:00.000Z"
}
```

### 字段说明

- `enabled`
  - 是否启用 139 云盘能力总开关
- `provider`
  - 当前固定为 `cmcc139`，为未来多云扩展预留
- `loginMode`
  - `password`：账号密码登录
  - `sms`：短信验证码登录
  - `session`：高级模式，手动录入会话
- `account`
  - 登录账号，通常为手机号
- `savePassword`
  - 是否允许系统保存加密后的密码，用于自动续登录
- `passwordEncrypted`
  - 加密后的密码，仅在允许保存密码时写入
- `sessionBundleEncrypted`
  - 加密后的会话材料，如 `authorization`、`mcloud-skey`、必要 cookie 等
- `authStatus`
  - `unknown` / `valid` / `expired` / `invalid` / `risk_control`
- `estimatedExpireAt`
  - 系统基于校验结果估算出的失效时间

### 安全建议

为了满足“配置结构仍在原系统设置中”的要求，可以在逻辑结构上放在 `cloudDrive` 对象里；但接口对外返回时必须做脱敏：

- `passwordEncrypted` 不回显真实内容
- `sessionBundleEncrypted` 不回显真实内容
- 仅返回掩码、状态、时间戳、是否已保存等元信息


### 字段说明

  - 本频道是否启用自动上传
- `destinationType`
  - `familyAlbum`：家庭相册

- `selectorMode`

## 6.2 为什么不推荐 V1 直接做二维码登录

当前调研结论下，不推荐二维码登录作为 V1 主方案，原因如下：

- 普通 Web 首页未看到二维码登录作为默认入口
- 未确认存在可直接复用的官方二维码授权组件
- 即便存在二维码页面，也大概率存在跨域、回调、会话提取问题
- 相比之下，账号登录/短信登录的页面结构已明确可见，更适合先做可控实现

结论：

- **V1 先做账号登录 + 短信登录**
- **二维码登录保留为后续增强项**

## 7.2 登录验证服务设计

### 推荐实现方式

V1 推荐通过 **VPS 受控浏览器会话** 或 **VPS 统一登录服务** 完成登录验证。

原因如下：

- 前端页面无法直接跨域读取 `yun.139.com` 的登录态材料
- 现有上传接口依赖网页会话、签名头、cookie 等材料
- 登录、会话采集、校验、续期更适合集中在 VPS 执行

### 登录验证流程

#### 账号登录模式

1. 管理员在后台输入手机号和密码
2. 前端调用 Workers 接口
3. Workers 转发到 VPS 登录服务
4. VPS 执行官方网页登录流程
5. VPS 提取必要会话材料
6. VPS 调用轻量查询接口进行验证
7. VPS 返回验证结果
8. Workers 保存脱敏元数据与加密凭证

#### 短信登录模式

1. 管理员输入手机号，点击“获取验证码”
2. VPS 发起短信流程
3. 管理员输入验证码并点击“登录验证”
4. VPS 完成登录并提取会话材料
5. VPS 调用轻量查询接口验证
6. 保存结果

#### 手动会话模式

1. 管理员输入会话材料
2. VPS 直接执行验证接口
3. 返回是否有效

## 7.3 上传任务触发设计

### 上传触发点

上传只在“最终 MP4 已确认可用”后触发，触发点包括：

- `renameCompletedSegment()` 成功后
- `renameFinalSegment()` 成功后
- `RecordingRecoveryService` 修复历史录制文件成功后

### 标准流程

1. 文件完成转换并重命名
2. 读取频道 `recordConfig.upload`
3. 若未启用自动上传，则结束
4. 若系统级 `cloudDrive.enabled` 为关闭，则结束
5. 创建上传任务记录
6. 将任务加入上传队列
7. 队列串行或限流并发执行上传
8. 成功后写入成功标记
9. 失败后按策略重试

---

## 7.4 上传状态与幂等设计

建议采用文件侧标记方案，而不是一开始就引入新数据库。

### 推荐方案

为每个最终 MP4 文件写一个同名状态文件，例如：

- `xxx.mp4.upload.json`

内容示例：

```json
{
  "status": "success",
  "destinationType": "familyAlbum",
  "groupId": "1167813833499519836",
  "albumId": "1244462741363734839",
  "fileSha256": "...",
  "fileSize": 17558798,
  "uploadedAt": "2026-03-16T00:00:00.000Z",
  "remoteFileId": "FkFz3sT4lIWoiyNzQpHdB6YOJLe9VJTVq",
  "retryCount": 1,
  "lastError": ""
}
```

### 这样设计的优点

- 不引入新数据库，符合当前项目轻量化风格
- 与录制文件天然绑定
- 服务重启后可扫描恢复
- 易于判断是否已上传成功，避免重复上传

### 幂等判断规则

以下条件任一满足，即认为文件已成功上传，不再重复提交：

- 存在 `.upload.json` 且状态为 `success`
- 上传接口返回“秒传成功”并已写入成功标记
- 上传前扫描发现远端已存在同一目标和相同哈希文件

---

## 7.5 139 上传执行逻辑设计

### 统一流程

1. 读取文件大小与 SHA256
2. 根据目标类型解析上传目标
3. 调用 `create`
4. 判断是否为 `rapidUpload`
5. 若为秒传，直接标记成功
6. 若不是秒传，则执行 `PUT`
7. 执行 `complete`
8. 写入 `.upload.json`

### 家庭相册模式

需要使用：

- `groupId`
- `albumId`
- `accountUserId`
- 当前有效登录态

### 默认文件目录模式

当前设计预留以下信息：

- `catalogId`
- `manualPath`
- `resolvedPath`

具体接口在 V1 中先做“路径验证 + 目录目标写入”，待目录树接口稳定后增强。

## 8. 登录过期与续期方案

## 8.1 你提出方案的优点与不足

你提出的思路是：

- admin 在线时，每半小时检查一次
- 如果过期，弹出中国移动云盘重新登录验证框

这个思路的优点是：

- 用户体验清晰
- 管理员能及时感知问题

但仅靠这个方案还不够，原因是：

- 录制上传发生在 VPS，不一定要求 admin 当时在线
- 如果 admin 不在线，上传任务仍可能继续产生
- 仅前端检查无法保证服务端第一时间发现失效

因此推荐做成 **前后端双层检查机制**。

---

## 8.2 推荐过期检测方案

### 服务端检测

服务端负责两个层面的检测：

#### 1）定时心跳检测

- VPS 每 15 分钟执行一次轻量会话校验
- 校验接口建议选择“查询相册列表”或“读取账号可见目录”的轻量接口

#### 2）上传前即时检测

- 每次真正上传前先校验当前会话状态
- 如果已失效，则不再继续上传，直接把任务标记为 `paused_auth_expired`

### 前端检测

当前管理员在线时：

- 每 30 分钟轮询一次 `/api/admin/cloud-drive/auth-status`
- 如果状态为 `expired` / `invalid` / `risk_control`
- 弹出重新登录验证框

---

## 8.3 推荐续期策略

### V1 推荐策略：人工重绑定

V1 不建议承诺“完全自动续登录”，推荐逻辑：

- 会话过期后，上传任务暂停
- admin 在线时弹窗提醒重新登录
- 重登录成功后，自动恢复队列中暂停任务

优点：

- 安全边界清晰
- 不依赖未确认的自动登录协议
- 实现风险最低

### V2 可选策略：自动续登录

如果后续账号登录链路稳定，并允许保存加密密码，可增加：

- 服务端自动尝试重新登录
- 失败后再回退为人工重绑定

但该策略风险更高：

- 风控可能拦截
- 密码保存安全要求更高
- 账号异常、短信挑战、设备校验等都可能打断自动流程

因此建议：

- **V1 不承诺自动续登录**
- **V2 再评估自动续登录**

## 11. 风险与注意事项

## 11.1 登录协议变动风险

139 云盘网页登录与上传接口明显依赖会话头、签名头和 cookie，存在以下风险：

- 前端版本升级后请求头格式变化
- 风控策略收紧
- 某些签名字段生成逻辑变化

应对方式：

- 登录和上传逻辑封装为独立服务
- 将会话采集、验证、上传、目录查询分层
- 保留“手动会话模式”作为应急降级方案

## 11.2 默认目录接口不稳定风险

当前家庭相册链路已较清晰；默认文件目录链路尚需进一步确认。

应对方式：

- V1 先上手动路径验证
- 树选择器放到 V1.1

## 11.3 账号安全风险

如果允许保存密码，必须额外注意：

- 只能保存加密后的密码
- 页面不回显密码
- 修改系统设置时要进行管理员权限校验
- 登录验证与状态查询接口都必须严格鉴权

## 11.4 会话过期导致任务堆积风险

如果登录过期后持续录制，未上传任务会积压。

应对方式：

- 上传状态文件持久化
- 会话恢复后自动补传
- 后台显示“待补传数量”

## 12. 最终推荐方案

综合当前调研结果，最终推荐如下：

### 12.1 登录方案

- **V1 主方案：账号登录 + 短信登录**
- **二维码登录：暂不作为主方案**
- **开放平台正式合作接入：长期可探索，但不作为当前落地前提**

### 12.2 配置结构

- 系统设置：扩展 `system:cleanup:config.cloudDrive`
- 频道配置：扩展 `channel:{id}.recordConfig.upload`

### 12.3 目录选择方案

- 家庭相册：V1 做可视化选择
- 默认文件目录：V1 先做手动路径 + 验证，V1.1 再做树形选择器

### 12.4 上传触发方案

- 在 MP4 标准化重命名完成后触发上传
- 同时覆盖恢复服务修复后的文件

### 12.5 过期处理方案

- 服务端 15 分钟主动探测
- 前端 admin 在线时 30 分钟轮询提醒
- 失效后暂停任务，重登录成功再恢复
- V1 不承诺自动续登录
