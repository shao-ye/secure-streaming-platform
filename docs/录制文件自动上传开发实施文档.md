## 1. 需求描述

### 1.1 业务场景

1. 幼儿园每个教室对应一个直播频道，每天按固定时间段录制
2. 录制文件先保存在 VPS 本地 `/srv/filebrowser/yoyo-k/{channelId}/{date}/` 目录
3. 开启"自动上传"后，录制结束的文件应该被**自动上传到 139 云盘**（家庭相册 / 个人网盘），方便家长后续查看、分享、归档
4. 系统要避免：**重复上传**、**漏传**、**把 139 账号搞到触发风控**

### 1.2 功能范围

本次实施**只覆盖**：

- 家庭相册方向的上传链路（`destinationType = 'familyAlbum'`）
- 对应的状态管理、失败重试、节流、通知接口骨架

本次实施**不覆盖**：

- 个人网盘（`destinationType = 'cloudFile'`）的上传（后续迭代，接口模式类似可复用本次框架）
- 邮件通知的实际发送（仅预留接口，后续独立实现）
- 登录态自动续期（总体蓝图 V2 才考虑）

### 1.3 关键需求点（来自本轮讨论确认）

| # | 需求项 | 确认结论 |
|---|---|---|
| 1 | 触发时机 | 录制文件改名 / 转标准 MP4 完成后立即触发入队 |
| 2 | 上传并发 | 全局串行，同时只有 1 个文件在传 |
| 3 | 节流 | 前一个文件传完 + 等 15 秒 → 开始下一个 |
| 4 | 幂等标记 | **上传成功后在文件名末尾加 `_u`**，失败不改名字 |
| 5 | 防重复入队 | 内存 `pendingSet + uploadingSet` 双重防护 |
| 6 | 重试次数 | 同一次入队内最多重试 3 次，失败直接放弃（文件名保持原样，由下次扫描/触发再次入队） |
| 7 | 失败通知 | 预留 `UploadNotifier` 接口，本次仅 `logger.error`，后续接邮件 |
| 8 | 启动恢复 | 服务启动时扫录制目录，非 `_temp_` 且非 `_u` 的文件都入队 |
| 9 | 兜底扫描 | 每小时定时扫一次，防止触发点漏掉 |
| 10 | 登录态检查 | 每次上传开始前检查登录态，失效则暂停队列 + 通知接口 |

```js
const fileBuffer = fs.readFileSync(filePath);
```

```
原文件 500MB
  ├─ Node 内存 fileBuffer        ≈ 500MB
  ├─ Node 内存 fileBase64        ≈ 670MB  (+33%)
  ├─ CDP 序列化传给浏览器          ≈ 670MB
  ├─ 浏览器 atob 转 Blob          ≈ 500MB

```

真实场景下一个录制分段可达 1GB，走这条路径 VPS 必 OOM。**这是迭代 1 的核心目标**。

## 3. 整体设计方案

### 3.1 数据流图

```
┌─── 录制中实时触发 ───┐       ┌── 启动/定时兜底扫描 ──┐
│ convertSegmentToStd │       │ 扫录制目录             │
│     ↓ resolve       │       │   跳过 _temp_          │
│ fs.renameSync(#3#5) │       │   跳过 _u.mp4$         │
│     ↓ finish        │       │   入队其余            │
└──────────┬──────────┘       └──────────┬────────────┘
           │                              │
           └──────────┬───────────────────┘
                      ▼
          FileFinalizeDispatcher.onFinalize(filePath, channelId)
                      │
                      ├─ 读取频道 recordConfig.upload
                      │  （若 enabled=false 或 destinationType 不支持，直接 return）
                      │
                      ▼
              UploadQueueService.enqueue(task)
                      │
                      ├─ 检查 pendingSet / uploadingSet 防重
                      └─ 入队
                      │
                      ▼
          CloudUploadWorker（单例，串行消费）
                      │
    ┌─────────────────┴─────────────────┐
    │ 1. 从队列取一条任务 → uploadingSet  │
    │ 2. 登录态检查                       │
    │    └─ 失效 → 暂停 + 通知 + 回退队列 │
    │ 3. 文件完整性检查（size / mtime）   │
    │    └─ 失败 → 通知 + 丢弃            │
    │ 4. 调 HybridUploader.upload()      │
    │    ├─ 成功 → rename 加 _u → 出队    │
    │    └─ 失败 → attempts++             │
    │         ├─ < 3: 等 5s 重试          │
    │         └─ ≥ 3: 通知 + 出队（文件名不变） │
    │ 5. 等 15 秒 → 回到第 1 步          │
    └─────────────────────────────────┘
```

### 3.2 文件名状态机

```
xxx_to_yyyyyy_temp_001.mp4   ← 正在录制（FFmpeg 在写）       【跳过】
xxx_to_yyyyyy.mp4            ← 录制完成，未传 / 待传 / 上次失败【入队】
xxx_to_yyyyyy_u.mp4          ← 已上传成功                    【跳过】
```

**为什么没有 `_uploading` 中间态**：
经讨论确认不需要。进程崩溃时上传中的文件保持原名（没 `_u`），重启扫描会自动再次入队 → 重传（依赖 139 的 SHA256 秒传能力兜底）。引入 `_uploading` 反而会导致上传到云盘的文件名带 `_uploading` 后缀，不可取。

**为什么没有 `_ufailed` 失败终态**：
经讨论确认不需要。失败不改文件名，等下次扫描重新入队，靠通知接口告知哪个文件失败即可。

### 3.3 关键组件一览

| 组件 | 是否新建 | 职责 |
|---|---|---|
| `HybridUploader`（改造） | 已存在 | 单文件流式上传到 139 家庭相册；移除 base64 全文件读取 |
| `UploadQueueService` | **新建** | 任务入队、出队、防重；内存队列即可，不做持久化 |
| `CloudUploadWorker` | **新建** | 串行消费队列；节流、重试、调用上传器、写标记 |
| `FileFinalizeDispatcher` | **新建** | 所有改名触发点的统一回调入口；根据 channelId 拉 recordConfig，决定是否入队 |
| `UploadNotifier` | **新建** | 失败 / 登录态失效的通知接口骨架；本次仅 logger.error |
| `RecordingUploadScanner` | **新建** | 启动扫描 + 定时兜底扫描 |
| `SimpleStreamManager`（改造） | 已存在 | 3 处改名成功后调用 `FileFinalizeDispatcher.onFinalize` |

## 5. 迭代 1：修复 HybridUploader 内存炸弹

### 5.1 目标

把 `HybridUploader.upload()` 从"全文件 base64 → 浏览器 atob"模式改造为**流式 PUT**，让单次上传内存峰值降到 50MB 以内（无论原文件多大）。

### 5.2 为什么必须先做

- 不修复这个，迭代 2/3 再完美，第一个 1GB 文件上传时 VPS 直接 OOM，整个上传链路不可用
- 修复后的上传器是迭代 2 Worker 的核心依赖

### 5.3 技术方案

当前流程（有问题）：

```
Node: fs.readFileSync() → toString('base64')
    ↓ 通过 page.evaluate 参数传递
Browser: atob() → Blob → fetch PUT
```

新流程（推荐方案 A：Node 侧直接 PUT）：

```
Node:
  1. page.evaluate 里调 `POST /hcy/group/dynamic/file/create`
     （这一步需要浏览器的 cookie + sign，保留在浏览器内）
     返回 uploadUrl + uploadId
  2. Node 侧直接用 fetch 发 PUT（Node 18+ 的 fetch 原生支持 ReadableStream）
     body = fs.createReadStream(filePath)
     duplex: 'half'
  3. 拿到 ETag 后再 evaluate 回浏览器，调 `file/complete`
```

**关键点**：
- `file/create` 和 `file/complete` 依赖 139 的 mcloud-sign，这两步**必须留在浏览器里**（保持现状，浏览器环境会自动处理 sign）
- `PUT uploadUrl` 是预签名 URL，**不需要 sign**，任何 HTTP 客户端都可以发，所以可以搬到 Node 侧用流式
- 测试时注意：139 预签名 URL 可能有有效期（初步估计 30 分钟~1 小时），流式 PUT 一个 1GB 文件走普通带宽 5~10 分钟，不会超时

**备选方案 B（如方案 A 遇阻）**：在浏览器里用 `fetch(uploadUrl, { body: stream })`，通过 `ReadableStream` 分段读取文件 —— 但浏览器无法直接读本地文件系统，需要走 Playwright 的 `page.route` 或 `CDP` 注入文件块，复杂度更高。**方案 A 失败才考虑**。

### 5.4 改动范围

- `vps-server/src/services/cloud-backup/hybrid-uploader.js`：重写 `upload(filePath)` 方法
- 其他文件不改

### 5.5 具体改造步骤

1. 把当前 `upload()` 中浏览器 evaluate 里的三步拆成三段独立的 page.evaluate：
   - 第一段：`createFileRecord(fileName, fileSize, contentHash, groupId, targetAlbumId)` → 返回 `{ fileId, rapidUpload, uploadUrl, uploadId }`
   - 第二段：**跳过浏览器**，Node 侧 `fetch(uploadUrl, { method: 'PUT', body: createReadStream, duplex: 'half' })` → 拿 ETag
   - 第三段：`completeFileUpload(uploadId, etag)`（如果 139 要求显式 complete）
2. 处理秒传分支：如果 `createFileRecord` 返回 `rapidUpload: true`，跳过 PUT 和 complete，直接返回成功
3. 上传过程中添加进度日志（例如每 10% 打一次 log）
4. `finally` 里正确 `browser.close()`（现状已实现）

### 6.3 UploadQueueService 设计

#### 6.3.1 数据结构

```js
// 内存队列，进程重启即失效（依赖迭代 3 的扫描器重建）
queue = [
  {
    filePath: '/srv/filebrowser/yoyo-k/.../xxx.mp4',
    channelId: 'stream_ensxma2g',
    uploadConfig: {  // 入队时的快照，防止运行中改配置出问题
      destinationType: 'familyAlbum',
      groupId: '...',
      albumId: '...',
      targetName: 'test12',
      retryTimes: 3
    },
    enqueuedAt: 1713590000000
  },
  ...
]

pendingSet = Set<filePath>   // 所有在队列中但还没被 Worker 取走的
uploadingSet = Set<filePath> // Worker 正在处理的
```

#### 6.3.2 公开方法

```js
/**
 * 入队一个上传任务
 * @param {Object} task 上传任务
 * @returns {boolean} 是否入队成功（重复则返回 false）
 */
enqueue(task): boolean

/**
 * 出队一个任务（FIFO）
 * @returns {Object|null}
 */
dequeue(): Object | null

/**
 * Worker 开始处理任务（加入 uploadingSet）
 */
markUploading(filePath): void

/**
 * Worker 完成任务（从 uploadingSet 移除）
 */
markFinished(filePath): void

/**
 * 查询队列状态
 */
getStatus(): { pending: number, uploading: number, items: [...] }
```

#### 6.3.3 关键实现点

- `enqueue` 前先检查：`pendingSet.has(filePath) || uploadingSet.has(filePath)` → 已在处理，跳过
- 线程安全：Node 是单线程，不需要锁，但 `async` 函数里要小心状态变更顺序

### 6.4 CloudUploadWorker 设计

#### 6.4.1 核心循环

```js
/**
 * Worker 主循环：永远运行，空闲时等待
 */
async runLoop() {
  while (this.running) {
    try {
      const task = this.queue.dequeue();
      if (!task) {
        await this.sleep(5000);  // 队列空，等 5 秒再查
        continue;
      }
      this.queue.markUploading(task.filePath);
      await this.processTask(task);
      this.queue.markFinished(task.filePath);
      await this.sleep(15000);  // 节流：下一个任务前等 15 秒
    } catch (err) {
      logger.error('UploadWorker loop error', { error: err.message });
      await this.sleep(5000);
    }
  }
}
```

#### 6.4.2 单任务处理流程

```js
async processTask(task) {
  const { filePath, channelId, uploadConfig } = task;
  const fileName = path.basename(filePath);

  // 步骤 1：登录态检查
  const loginOk = await this.checkLoginStatus();
  if (!loginOk) {
    await this.notifier.notifyLoginExpired({ filePath });
    this.pauseQueue();  // 暂停 Worker，等下次 resume
    // 把当前 task 回退队列头
    this.queue.requeueHead(task);
    return;
  }

  // 步骤 2：文件完整性检查
  if (!fs.existsSync(filePath)) {
    logger.warn('Upload target file disappeared', { filePath });
    return;
  }
  const stat = fs.statSync(filePath);
  if (stat.size < 1024 * 1024) {  // 小于 1MB，可能是空文件
    await this.notifier.notifyUploadFailed({
      filePath, reason: 'file_too_small', size: stat.size
    });
    return;
  }
  if (Date.now() - stat.mtimeMs < 5000) {
    // mtime 距现在不到 5 秒，可能还在写，跳过，等下次扫描
    logger.info('File mtime too recent, skip this round', { filePath });
    return;
  }

  // 步骤 3：实际上传，最多重试 3 次
  for (let attempt = 1; attempt <= uploadConfig.retryTimes; attempt++) {
    try {
      logger.info('Upload attempt start', { filePath, attempt });
      const result = await this.hybridUploader.upload(filePath, uploadConfig);
      // 成功：加 _u 标记
      await this.renameWithSuccessMark(filePath);
      logger.info('Upload success', { filePath, attempt, result });
      return;
    } catch (err) {
      logger.error('Upload attempt failed', {
        filePath, attempt, error: err.message
      });
      if (attempt < uploadConfig.retryTimes) {
        await this.sleep(5000);  // 重试间隔 5 秒
      } else {
        // 最后一次仍失败
        await this.notifier.notifyUploadFailed({
          filePath, attempts: attempt, lastError: err.message
        });
        // 文件名保持原样，下次扫描会重新入队
      }
    }
  }
}
```

### 7.3 FileFinalizeDispatcher 设计

```js
class FileFinalizeDispatcher {
  constructor({ uploadQueue, channelConfigFetcher }) {
    this.queue = uploadQueue;
    this.fetchChannelConfig = channelConfigFetcher;
  }

  /**
   * 录制文件改名/标准化完成后的统一回调
   * @param {string} filePath 最终文件路径（不带 _u，不含 _temp_）
   * @param {string} channelId
   */
  async onFinalize(filePath, channelId) {
    try {
      // 1. 获取频道的上传配置
      const config = await this.fetchChannelConfig(channelId);
      const uploadCfg = config?.recordConfig?.upload;

      // 2. 上传未启用，直接返回
      if (!uploadCfg || !uploadCfg.enabled) {
        logger.info('Upload not enabled for channel, skip', { channelId });
        return;
      }

      // 3. 当前只支持家庭相册，其他类型跳过
      if (uploadCfg.destinationType !== 'familyAlbum') {
        logger.info('Only familyAlbum supported in this iteration', {
          channelId, destinationType: uploadCfg.destinationType
        });
        return;
      }

      // 4. 入队
      const enqueued = this.queue.enqueue({
        filePath,
        channelId,
        uploadConfig: { ...uploadCfg },  // 快照
        enqueuedAt: Date.now()
      });
      if (enqueued) {
        logger.info('File enqueued for upload', { filePath, channelId });
      }
    } catch (err) {
      logger.error('FileFinalizeDispatcher onFinalize error', {
        filePath, channelId, error: err.message
      });
    }
  }
}
```

### 7.6 RecordingUploadScanner 设计

```js
class RecordingUploadScanner {
  /**
   * 服务启动时扫一次 + 每小时扫一次
   */
  async start() {
    // 启动时延迟 30 秒后扫，让 RecordingRecoveryService 先跑完
    setTimeout(() => this.scanAll(), 30 * 1000);
    // 每小时一次
    setInterval(() => this.scanAll(), 60 * 60 * 1000);
  }

  async scanAll() {
    const recordingsRoot = process.env.RECORDINGS_PATH || '/srv/filebrowser/yoyo-k';
    // 递归找所有 .mp4 文件
    const files = await this.findAllMp4Files(recordingsRoot);
    logger.info('UploadScanner found files', { total: files.length });

    for (const filePath of files) {
      const name = path.basename(filePath);

      // 跳过 _temp_（正在录制）
      if (name.includes('_temp_')) continue;

      // 跳过 _u.mp4（已上传）
      if (/_u\.mp4$/i.test(name)) continue;

      // 只处理符合录制命名规则的
      if (!/_to_\d{6}\.mp4$/i.test(name)) continue;

      // 反推 channelId（目录结构：{root}/{channelId}/{date}/file.mp4）
      const channelId = this.extractChannelId(filePath, recordingsRoot);
      if (!channelId) continue;

      await this.dispatcher.onFinalize(filePath, channelId);
    }
  }
}
```

## 10. 风险与回滚预案

### 10.1 HybridUploader 流式改造失败

**风险**：139 预签名 URL 拒绝 Node 侧直接 PUT（比如校验 User-Agent、Referer 等）。

**应对**：
- 抓包对比浏览器 PUT 和 Node PUT 的完整请求头，手动补齐
- 实在不行，回退方案 B（浏览器内分段流式）
- 再不行，保留 base64 路径但加 **文件大小上限保护**（> 100MB 不允许上传，避免 OOM；虽然这样就不能用了，但至少不会炸服务）

### 10.2 上传触发后频繁打扰录制主流程

**风险**：`renameCompletedSegment` 每次分段切换都会触发 dispatch，如果 dispatch 里有慢操作（如 axios 拉 channelConfig 超时），会拖慢录制。

**应对**：
- `dispatcher.onFinalize` 内部用 `setImmediate` 异步执行，**立即返回不阻塞调用方**
- `axios.get` 有 3 秒 timeout，不会无限等

### 10.3 队列无持久化，重启丢失

**风险**：队列里还有任务时服务重启，任务丢失。

**应对**：
- 依赖 `RecordingUploadScanner` 启动扫描重建（30 秒后扫一遍）
- 所有"未 `_u` 的文件"都会被重新入队
- **可接受**：扫描 + 15 秒节流可能延迟若干分钟，但不会漏传

### 10.4 139 侧风控

**风险**：短时间上传大量文件触发 139 账号风控（IP 被封、账号被限制）。

**应对**：
- 15 秒节流是主要手段
- 如触发风控，`UploadNotifier` 记录，暂停队列，等人工介入
- 可以考虑后续加**每日上传总量上限**（如每天最多 200 个文件，超过则暂停到第二天）

### 10.5 回滚方案

每个迭代都是独立的 git commit，可单独回滚：
- 迭代 1 回滚：`git revert <iter1-commit>` → `HybridUploader` 回到 base64 版（功能仍可用但有 OOM 风险，回滚后不要上传大文件）
- 迭代 2 回滚：Worker 不启动，队列 API 返回 404，不影响录制
- 迭代 3 回滚：`onFinalize` 调用点改为空操作，不影响录制
