# 中国移动云盘扫码登录设计文档

## 1. 文档目标

本文档设计以下能力，当前阶段只做方案设计与评审，**不改业务代码**：

- 在现有“短信验证码登录”旁新增一种**二维码扫码登录**方式
- 保留旧的短信登录，不破坏现有配置与上传链路
- 解决当前短信登录受 139 官网限频、滑块风控拦截，导致验证码不到达或出现“假成功”的问题
- 给出与现有 `CloudDriveLoginExecutor` / `CloudDriveService` 共存的工程方案

---

## 2. 背景与动机

### 2.1 当前链路存在的真实问题

根据线上实测：

- 手机号 `138****8000` 通过前端点击“获取验证码”后，**手机未收到短信**，直接在 `https://yun.139.com/` 登录页触发也不到
- VPS 状态文件 `data/cloud-drive/state.json` 中曾出现：
  - `authMessage = 官网滑块验证失败次数超过限制，请稍后重试`
- VPS 状态文件后续又出现：
  - `authMessage = 验证码已发送，请输入短信验证码完成登录`
  - 但手机上依旧未收到

这说明：

- 当前短信链路被 139 风控命中，短期冷却窗口已打开
- 且 `CloudDriveLoginExecutor.analyzeSmsRequestResult` 使用“页面文案 / 按钮倒计时 / 重新获取”作为成功旁证，**存在“看起来成功，实际未投递短信”的假成功可能**

### 2.2 为什么选择扫码登录

通过对 `https://yun.139.com/` 与 `https://yun.139.com/w/` 的非侵入式踩点，已确认：

- QRCode 是 139 官方一等登录方式，与 `passSMS / passPwd / SIM` 并列
- 官网前端常量表存在完整的扫码状态枚举与错误码：
  - `qrCodeErrArr: ["200059543","200059545","200059546","200059547"]`
- 官网前端存在完整 i18n 状态提示：
  - `To_scan_and_log_in = 扫码登录`
  - `Using_your_phone_to_scan_the_QR_code = 请打开手机，扫码上方二维码`
  - `Please_confirm_login_on_your_mobile_devi = 请在手机端登录确认`
  - `Cancelled_please_scan_again = 已取消，请重新扫描`
  - `The_QR_code_is_invalid = 二维码已失效`

扫码登录天然具备以下优势：

- **不触发短信通道**，不受运营商限频影响
- **不触发滑块拼图**，绕开现有脆弱的自动化拖拽
- 设备端由真人确认，安全合规，稳定性显著高于短信自动化
- 登录后产生的会话结构（cookies / localStorage / sessionStorage）与短信登录一致，**上传链路零改动即可复用**

## 3. 设计原则

- **新增不破坏旧能力**：短信登录继续保留，用户可在系统设置中切换
- **最小侵入 VPS 现有服务**：扫码登录执行器与现有 `CloudDriveLoginExecutor` 并列，不改旧类
- **无假数据**：Worker 层与 VPS 层**严禁**依据页面文案兜底生成“验证码已发送”或“登录成功”文案，一律透传官网真实状态
- **会话隔离**：每个扫码会话对应独立的 Playwright 上下文，禁止跨用户串扰
- **超时强释放**：扫码会话强制总超时，避免 VPS 积累僵尸浏览器
- **Worker KV 最小化访问**：Cloudflare 免费额度写仅 1000 次/天，扫码**轮询路径严禁读写 KV**，仅在登录成功时做 1 次读 + 1 次写落地；具体约束见 §7.6、§8.2、§17

## 4. 方案总览

### 4.1 架构视图

```
[前端 SystemSettingsDialog.vue]
        │   (1) 选择“扫码登录”并点击生成二维码
        ▼
[Cloudflare Worker /api/cloud-drive/qr/create]
        │   (2) 透传到 VPS
        ▼
[VPS CloudDriveQrLoginExecutor]
        │   (3) Playwright 打开 https://yun.139.com/w/#/
        │   (4) 等待二维码 DOM 出现并截取 canvas/img 位图 base64
        │   (5) 建立 sessionId -> (browser, context, page) 映射
        ▼
[VPS 响应]
        │   { sessionId, qrImageBase64, expireAt, status: 'pending' }
        ▼
[前端 轮询 /api/cloud-drive/qr/status?sessionId=xxx 每 2s]
        │
        ▼
[Worker 透传 → VPS 读取当前页面状态]
        │   - 扫码中: pending
        │   - 已扫码待确认: awaiting_confirm
        │   - 已登录: success，立即 captureSessionBundle
        │   - 已取消 / 已失效 / 未知错误: expired | cancelled | error
        ▼
[VPS 写入 state.json + 关闭 Playwright 上下文]
        ▼
[前端 展示最终结果]
```

### 4.2 与现有短信登录共存方式

- 新增配置字段：`loginMode`
  - 旧：仅 `sms`
  - 新：`sms` | `qrcode`
- 前端按 `loginMode` 渲染不同表单
- 后端按 `loginMode` 路由到不同执行器
- 登录成功后产生的 sessionBundle 结构保持不变，**上传链路无感知**

## 5. 状态机

二维码扫码会话共有 7 种状态，均直接映射 139 官网真实状态或本地超时：

- `pending`：二维码已生成，等待用户手机扫码
- `awaiting_confirm`：用户已扫码，等待手机端点击确认登录
- `success`：登录成功（已抓取到 sessionBundle）
- `expired`：二维码已过期（139 页面提示“二维码已失效”或本地到期）
- `cancelled`：用户手机端取消（139 页面提示“已取消，请重新扫描”）
- `error`：官网返回 `qrCodeErrArr` 中的错误码或其他未知错误
- `timeout`：本地扫码总超时强制关闭

状态机流转：

```
pending ──(手机扫码)──► awaiting_confirm
pending ──(用户或后端取消)──► cancelled
pending ──(到期)──► expired
awaiting_confirm ──(手机端确认)──► success
awaiting_confirm ──(手机端取消)──► cancelled
awaiting_confirm ──(到期)──► expired
pending | awaiting_confirm ──(本地超时)──► timeout
任意非终态 ──(未识别错误)──► error
```

终态：`success` | `expired` | `cancelled` | `error` | `timeout`  
到达终态后 VPS 必须释放该会话对应的 Playwright 上下文。

## 6. 前端设计

### 6.1 UI 改动位置

- 文件：`frontend/src/components/admin/SystemSettingsDialog.vue`
- 位置：现有“中国移动云盘配置”区域

### 6.2 交互流程

- 新增单选组：
  - 登录方式
    - 短信验证码登录
    - 扫码登录（默认）
- 切换到“扫码登录”后显示：
  - 按钮：生成二维码
  - 区域：二维码图片（base64）
  - 区域：扫码状态文案
  - 区域：有效期倒计时
  - 按钮：重新生成（到期 / 取消后出现）
- 切换回“短信验证码登录”时，不清除已有 sessionBundle

### 6.3 轮询策略

- 点击“生成二维码”后：
  - 立刻调 `POST /api/cloud-drive/qr/create`
  - 展示二维码 + 开始倒计时
  - 启动定时器 `setInterval(2000)` 调用 `GET /api/cloud-drive/qr/status?sessionId=xxx`
- 终态命中时：
  - 清除定时器
  - 展示最终文案（复用官网真实文案）
  - `success` 时**直接复用** `qr/status` 响应中已返回的 `cloudDrive` 字段更新表单展示
  - **禁止**再额外调用 `/api/cloud-drive/auth-status`（那一次调用会产生 1 读 + 1 写 KV，白白浪费配额）
- 页面 `unmounted` 时：
  - 发 `POST /api/cloud-drive/qr/cancel` 主动释放
- 最长显示时长：
  - 前端本地控制上限 3 分钟
  - 超过后自动判为 `timeout` 并调用 cancel

## 7. 后端设计（VPS）

### 7.1 新增类

- 文件：`vps-server/src/services/cloud-drive/CloudDriveQrLoginExecutor.js`
- 与现有 `CloudDriveLoginExecutor.js` 并列，不修改旧类

关键职责：

- `createQrSession()`：创建 Playwright 上下文并返回二维码位图
- `pollQrSession(sessionId)`：返回真实扫码状态
- `cancelQrSession(sessionId)`：强制释放
- `disposeIfExpired()`：定时清理超时会话

### 7.2 二维码采集策略

优先级：

- 第一优先：定位包含二维码的 img 元素，若其 `src` 是 base64，则直接返回
- 第二优先：若二维码用 canvas 渲染，则 `canvas.toDataURL('image/png')` 返回 base64
- 第三优先：若以上均失败，则对二维码外层容器 `elementHandle.screenshot()` 截图并转 base64

三者都失败时返回 `error` 状态并销毁会话。

### 7.3 扫码状态采集策略

按以下顺序判断：

- 是否已经跳转到登录后视图（`#/index` | `#/familycloud` 等已知登录后路由）
  - 若是：立即 `success`
- 是否出现“请在手机端登录确认”文案或等效 DOM
  - 若是：`awaiting_confirm`
- 是否出现“已取消”文案
  - 若是：`cancelled`
- 是否出现“二维码已失效”文案
  - 若是：`expired`
- 是否可从官方前端 Vue 实例中读取到 `qrCodeErrArr` 中定义的错误码
  - 若是：`error`，并透传原始错误码
- 以上都未命中：保持 `pending`

**禁止**：

- 不以任何“看起来像成功”的页面文案兜底生成 `success`
- 不以倒计时存在与否推断成功
- 不隐藏官网返回码，必须透传到前端

### 7.4 会话管理

- 每个 sessionId 对应：
  - 一个 Playwright `browser`
  - 一个 `context`
  - 一个 `page`
  - 一个 `createdAt`
  - 一个 `lastCheckedAt`
- 全局最多允许 N 个活跃会话（建议 N=3）
- 同账号（同后台用户）**只允许 1 个活跃会话**，新建时先 cancel 旧的
- 后台定时器每 30 秒清理 `createdAt` 距当前超过 3 分钟的会话

### 7.5 会话捕获

- 复用现有 `captureSessionBundle(context, page)` 方法
- 不破坏现有 sessionBundle 结构，使上传侧无感知

### 7.6 KV 访问边界

- VPS 端**全程不直接访问 Cloudflare Worker KV**
- VPS 端所有会话状态仅保存在进程内存 + 本地 `data/cloud-drive/state.json`
- 所有排障字段（例如 `lastProviderCode`、`lastProviderMessage`）只落 `state.json`，不上 KV
- VPS 返回给 Worker 的响应需自带 `cloudDrive` 对象，Worker 在 `state === 'success'` 时直接以该对象覆盖 KV，避免 Worker 侧再 1 次读 + 1 次写中间态

## 8. 接口设计

### 8.1 VPS 侧新增路由

文件：`vps-server/src/routes/cloud-drive.js`（在现有路由旁新增，不改旧路由）

- `POST /api/cloud-drive/qr/create`
  - 请求体：空
  - 响应：
    ```json
    {
      "status": "success",
      "data": {
        "sessionId": "uuid",
        "qrImageBase64": "data:image/png;base64,...",
        "expireAt": "2026-04-17T02:35:00.000Z",
        "state": "pending"
      }
    }
    ```
- `GET /api/cloud-drive/qr/status?sessionId=xxx`
  - 响应：
    ```json
    {
      "status": "success",
      "data": {
        "sessionId": "uuid",
        "state": "pending | awaiting_confirm | success | expired | cancelled | error | timeout",
        "providerCode": "200059545",
        "providerMessage": "原始官网文案",
        "cloudDrive": { ...仅在 success 时返回脱敏配置 }
      }
    }
    ```
- `POST /api/cloud-drive/qr/cancel`
  - 请求体：`{ "sessionId": "uuid" }`
  - 响应：`{ "status": "success" }`

### 8.2 Cloudflare Worker 侧新增路由

文件：`cloudflare-worker/src/handlers/cloudDriveHandler.js`

- 在 `handleCloudDriveRequest` 中追加：
  - `POST /api/admin/cloud-drive/qr/create`
  - `GET /api/admin/cloud-drive/qr/status`
  - `POST /api/admin/cloud-drive/qr/cancel`
- 内部调用 `callVpsCloudDrive(env, '/qr/create', ...)` 等
- **Worker 层仅做透传与脱敏，不做任何“成功文案兜底”**
- **KV 访问边界（强约束）**：
  - `POST /api/admin/cloud-drive/qr/create`：**不读 KV，不写 KV**
  - `GET /api/admin/cloud-drive/qr/status`：
    - `pending` / `awaiting_confirm` / `expired` / `cancelled` / `error` / `timeout` 分支：**不读 KV，不写 KV**
    - 仅当 VPS 返回 `state === 'success'` 时：**读 1 次 + 写 1 次**，把最新 `cloudDrive` 与 sessionBundle 指纹落 KV
  - `POST /api/admin/cloud-drive/qr/cancel`：**不读 KV，不写 KV**
- **禁止**在轮询路径任何 pending 分支里为“顺便记录 updatedAt”而写 KV
- **禁止**为补齐默认字段在每次轮询时都调用 `readSystemConfig`；轮询过程前端渲染所需的配置应完全由 VPS 响应中的 `cloudDrive` 对象提供

### 8.3 前端调用入口

文件：`frontend/src/components/admin/SystemSettingsDialog.vue`

沿用现有 axios 封装：

- `POST ${CLOUD_DRIVE_API_PREFIX}/qr/create`
- `GET ${CLOUD_DRIVE_API_PREFIX}/qr/status?sessionId=xxx`
- `POST ${CLOUD_DRIVE_API_PREFIX}/qr/cancel`

## 9. 数据结构改动

### 9.1 Worker KV `system:cleanup:config.cloudDrive`

KV 是计费资源，新增字段必须按以下原则归类：

- **允许落 KV 的新增字段**（跨请求持久、且前端渲染必需）：
  - `loginMode`
    - 取值：`sms` | `qrcode`
    - 默认：`qrcode`（新部署默认扫码）
- **禁止落 KV 的字段**（仅用于排障、不影响业务行为）：
  - `lastProviderCode`（最近一次官网返回码）
  - `lastProviderMessage`（最近一次官网真实文案）
  - 理由：
    - 这两个字段仅在扫码失败时短暂有意义，每次刷新都会变
    - 若落 KV，会在轮询失败场景下频繁写入，直接威胁写额度
    - 前端不依赖这两个字段即可完成基础渲染，只是排障辅助
  - 落地位置：改为写到 VPS 本地 `state.json`（见 §9.2）
- 其它字段不变
- `getDefaultCloudDriveConfig()` 默认值同步新增 `loginMode: 'qrcode'`

### 9.2 VPS 本地 `data/cloud-drive/state.json`

该文件只在 VPS 磁盘，不消耗 Cloudflare KV 配额，因此适合放“仅用于排障、会频繁变化”的字段：

- **新增字段**：`loginMode`（与 KV 冗余一份，便于 VPS 离线脚本排障）
- **新增字段**：`lastProviderCode`（最近一次官网返回码）
- **新增字段**：`lastProviderMessage`（最近一次官网真实文案）
- 其它字段保持与现在一致

这三个新字段仅用于排障和诊断，不影响上传，**不会同步到 KV**。

### 9.3 SessionBundle 结构

- 不变
- 继续沿用 `captureSessionBundle()` 抓取的 cookies / localStorage / sessionStorage
- 继续使用现有 AES 加密 + KV 持久化路径

## 10. 错误与异常

### 10.1 透传 139 官网错误

Worker 与 VPS 必须将下列字段原样透传给前端：

- `providerCode`：官网原始错误码（如 `200059545`）
- `providerMessage`：官网原始文案（不翻译、不重写）

### 10.2 本地兜底错误分类

仅在无法从官网获取任何线索时使用，且文案以 `[本地]` 开头，明确区分：

- `[本地] 二维码生成失败`
- `[本地] 扫码会话已超时`
- `[本地] 浏览器上下文启动失败`
- `[本地] 网络异常`

### 10.3 严禁行为

- 禁止在任何环境把“验证码已发送”“登录成功”类文案作为兜底返回
- 禁止在 VPS 的 state.json 中写入未经官网确认的 `authStatus: valid`
- 禁止在扫码流程中混入短信流程的 “滑块处理” 逻辑

---

## 11. 超时与资源回收

- 单个扫码会话总超时：**3 分钟**
- 每次轮询 `qr/status` 的 VPS 内部超时：**5 秒**
- 创建二维码总超时（含 Playwright 启动 + 页面就绪 + 截图）：**20 秒**
- VPS 进程退出 / 服务重启时统一关闭所有活跃 Playwright 实例
- `disposeIfExpired()` 每 30 秒巡检一次

---

## 12. 安全与隐私

- 二维码 base64 仅在 HTTPS 链路传输，不写入任何日志
- sessionId 使用服务端生成的 v4 UUID
- sessionBundle 在 KV 中存储时继续使用现有 AES 加密
- 日志中涉及手机号、token、cookie 值一律脱敏
- 扫码会话不接受外部用户提供的 sessionId 复用，防止会话劫持

## 14. 测试与验收

### 14.1 正向用例

- 生成二维码 → 手机扫码 → 手机确认 → 前端显示登录成功
- 登录后 `auth-status` 应返回 `authStatus: valid`
- 上传链路能正常复用该 sessionBundle 完成录制文件上传

### 14.2 异常用例

- 用户点击“生成二维码”但不扫 → 3 分钟后前端显示 `timeout`，VPS 无残留浏览器
- 扫码后手机端点击取消 → 前端显示“已取消，请重新扫描”
- 二维码过期 → 前端显示“二维码已失效”，提供“重新生成”
- VPS 在扫码中重启 → 前端在下一次轮询时收到 `error`，可重新生成

### 14.3 共存用例

- 用户已通过旧短信方式登录成功（已有 sessionBundle）
  - 切换到扫码方式时，旧 sessionBundle 不应被清除
- 用户通过扫码方式登录成功
  - 切换回短信方式时，扫码产生的 sessionBundle 仍然有效，上传不受影响

---

## 15. 回滚与灰度

- 灰度开关：`cloudDrive.loginMode` 默认 `qrcode`
- 线上出现严重问题时，前端把默认值改回 `sms` 即完成回滚
- VPS / Worker 的新增路由保持只读式追加，不影响旧路由
- 回滚无需数据库迁移，无需重启服务

## 16. 风险评估

- **风险 1**：139 官网可能对 QR 截图做防抓（如 WebGL 或 CSS 动态水印）
  - 缓解：采用三级降级策略（img src → canvas.toDataURL → element.screenshot）
- **风险 2**：官网页面 DOM 细节变动可能影响状态识别
  - 缓解：状态识别同时依赖 URL 路由、Vue 实例字段、文案三种信号
- **风险 3**：VPS 资源占用（Playwright 内存）
  - 缓解：同账号单会话，全局最多 3 会话，3 分钟强制释放
- **风险 4**：新旧登录方式字段冲突
  - 缓解：通过 `loginMode` 明确分流，sessionBundle 结构不变
- **风险 5**：Cloudflare KV 写额度（免费 1000/天）被轮询击穿
  - 场景：若 `qr/status` 在 `pending` 轮询阶段也写 KV，单会话 90 次轮询 × 多人并发，很快就会超额
  - 缓解 1：严格执行 §7.6 / §8.2 的“轮询路径不读写 KV”约束
  - 缓解 2：仅在 `state === 'success'` 分支做 1 次读 + 1 次写
  - 缓解 3：对现有高频 KV 读路径增加 `{ cacheTtl: 60 }`（见 §17.4）

## 17. KV 资源消耗与优化

### 17.1 Cloudflare Workers KV 免费额度

- 读：**100,000 次/天**
- 写：**1,000 次/天**（本方案最需要防守的一项）
- 删：1,000 次/天
- list：1,000 次/天
- 存储：1 GB
- 超额计费：读 0.5 美元/百万次，写/删/list 5 美元/百万次

### 17.2 当前真实 KV 消耗（未改造前保守估算）

按 10 频道 × 2 次录制窗口 + 管理员每天操作 5 次粗估：

- 涉及 `system:cleanup:config` 的读：约 40~50 次/天
- 涉及 `system:cleanup:config` 的写：约 15~20 次/天
- 距离免费额度仍有大量冗余

### 17.3 扫码方案 KV 预算（落地后的目标）

在严格执行 §7.6 / §8.2 的前提下：

- 单次扫码会话，Worker 侧 KV 开销：
  - 失败分支：**0 读 0 写**
  - 成功分支：**1 读 + 1 写**
- 管理员每天扫码 20 次（含失败重试）：
  - 读：+20
  - 写：+20
- 相对免费额度几乎可以忽略

### 17.4 现有高频 KV 读优化（与本方案并行）

建议给下列 `env.YOYO_USER_DB.get('system:cleanup:config', ...)` 调用追加 `{ cacheTtl: 60 }`：

- `cloudflare-worker/src/handlers/cloudDriveHandler.js` 的 `readSystemConfig()`
- `cloudflare-worker/src/index.js` 中 `/api/admin/cleanup/config` 的 GET 分支
- `cloudflare-worker/src/index.js` 中 `/api/admin/cleanup/config` 的 PUT 分支（先读后写，读侧可缓存）
- `cloudflare-worker/src/index.js` 中系统初始化 (`system:init` / `system:cleanup:config` 兜底创建) 分支

效果：

- 同一个 edge 节点 60 秒内的重复读取，只按 1 次计费读
- 对 VPS `VideoCleanupScheduler` / `RecordScheduler` 的周期读取、以及前端设置弹窗打开读取都有立即收益
- 不改业务语义、不改写路径，可作为独立小 PR 提前上线

### 17.5 VPS 侧配套建议（可选）

`RecordScheduler.fetchSystemSettings()` 当前每次开始录制都会向 Worker 拉一次 `/api/admin/cleanup/config`。建议：

- 在 VPS 进程内缓存 5 分钟 TTL
- 或与 `VideoCleanupScheduler` 共用一个读取层
- 进一步降低对 Worker 与 KV 的压力，但不是本方案落地的前置条件
